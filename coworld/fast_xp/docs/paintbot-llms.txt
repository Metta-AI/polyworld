# Paintbot fast-XP

Run full-speed Paintbot matches with POST /v1/games/paintbot-pw/run.
Send Content-Type: application/json. The hosted service is private to Softmax
Tailscale; no Authorization header is required from callers.

The JSON request supplies a signed 32-bit seed and a roster of bots:

{"seed":2026,"roster":[{"player":{"source":"idle = 1\n"}}],"config":{"max_ticks":240}}

This minimal example fills all 16 seats with an idle BASIC script. Replace it
with your complete bot. Each roster entry's player must contain exactly one of:
- source: raw BASIC text, up to 128 KiB.
- package_base64: a standard padded base64 ZIP in Paintbot's policy format.
- policy_ref: an exact submitted policy name:vN or policy-version UUID.

Upload your own bot with source or package_base64 and select opponents with
policy_ref. The server fetches submitted policies using its own credential.
Only uploaded seats' logs are returned; policy-reference logs and source remain
private, including when you own that submitted policy.

Roster entries optionally specify slot: 0–15 pins that seat; -1 (default) fills
open seats cyclically. Even seats are red, odd seats blue. At least one open
entry is needed unless every seat is pinned. Supply 1–16 entries.

num_episodes is optional, 1–10, default 1. Game i uses seed+i and rotates unpinned
entries; pinned seats stay fixed. config.max_ticks defaults to 14400 and accepts
1–28800. Other game configuration is fixed to the league's teams defaults.

Games run as fast as the CPU allows. JEV/oracle calls are unavailable; scripts
use the engine's normal no-oracle behavior. This does not test JEV strategies.

The response is a ZIP. One game contains replay.replay and logs/slot-N.txt for
uploaded seats. Batches contain manifest.json and games/000/, games/001/, etc.
Check each game's status in the manifest: HTTP 200 batches can contain failures.
There is no polling or stored result endpoint. Save the response before exiting.

The dashboard shows the current worker capacity; accepted games queue. Each game has a
300-second execution deadline, excluding queueing. Use a long HTTP timeout for
batches; a batch can wait behind other requests. 429 means request admission is
full; honor Retry-After. X-Request-ID correlates with server logs. Server-Timing
reports preparation (fetch), queue, worker, gameplay, ZIP, and total server
milliseconds. Gameplay includes bots and replay-frame recording within the tick
loop; worker also includes initialization and final artifact writing. Queue,
worker, and gameplay timings sum across games rather than measuring batch wall time.

GET / shows the dashboard. GET /healthz checks availability.
GET /docs/run.md explains packages, errors, and failure handling.
